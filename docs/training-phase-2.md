# 算法训练升级：阶段 2 验收

阶段 2 在阶段 1 的持久化远程执行器之上，交付训练配置、任务队列、用户权限、停止/取消、重试，以及普通用户可使用的任务管理页面。实时日志流和训练曲线属于后续阶段，本阶段页面以 5 秒轮询任务状态。

## 训练配置

迁移文件：`fastapi-app/migrations/004_training_management.sql`

- 为任务增加 `retry_of_job_id` 和 `attempt`，保留完整重试关系
- PBAS 参数由数据库中的 JSON Schema 驱动，前后端共用同一组字段和约束
- 当前开放参数：类别、训练轮数、批大小、学习率、数据线程、缩放/输入尺寸、随机种子和评估间隔
- 算法、数据集、GPU、入口、源码目录及运行环境继续受服务端白名单约束
- 用户不能提交 Shell 命令、任意入口、任意路径或 Schema 之外的参数

PBAS 当前限制为最多 10 个 epoch；该限制用于阶段验收，后续可通过数据库 Schema 与执行器白名单同步调整。

## 队列与 GPU 分配

新任务先持久化为 `QUEUED`，再由调度器尝试分配 GPU。分配同时检查：

- GPU 是否位于 `TRAINING_GPU_ALLOWLIST`
- 数据库中是否已有活动租约
- `nvidia-smi` 返回的真实剩余显存是否达到 `TRAINING_MIN_FREE_GPU_MEMORY_MB`

资源不足时任务保持 `QUEUED`，后台监控周期会继续调度。每个用户默认最多保留 3 个活动或排队任务，避免单个账号占满队列。

状态流转：

```text
QUEUED -> STARTING -> RUNNING -> SUCCEEDED
                         |          FAILED
                         +-------> STOPPING -> STOPPED

QUEUED --取消-----------> STOPPED
异常且不可追踪----------> LOST
```

`QUEUED` 没有远程进程，恢复器不会将它误判为 `LOST`。`STARTING` 在 launcher PID 尚未写回时有启动宽限期，避免启动与监控并发造成误判。

## 用户权限

- 普通用户只能查看、取消、停止和重试自己创建的任务
- 请求其他用户的任务统一返回 404，不泄露任务是否存在
- 管理员可以查看全部用户任务
- 重试会复制原任务的受控配置，创建新的任务编号，并递增 `attempt`
- 终态任务不可停止；排队任务使用取消操作

## 阶段 2 API

- `GET /training/options`：可用算法、数据集、GPU、参数 Schema 和队列额度
- `POST /training/jobs`：创建并尝试调度任务
- `GET /training/jobs`：分页查询当前用户任务；管理员查询全部任务
- `GET /training/jobs/{id}`：配置、事件、指标和产物详情
- `POST /training/jobs/{id}/cancel`：取消排队任务
- `POST /training/jobs/{id}/stop`：停止远程活动任务
- `POST /training/jobs/{id}/retry`：从终态任务创建新尝试

创建请求示例：

```json
{
  "algorithmId": 1,
  "datasetId": 1,
  "requestedGpu": null,
  "parameters": {
    "classes": ["screw"],
    "epochs": 5,
    "batch_size": 8,
    "learning_rate": 0.0001,
    "num_workers": 4,
    "resize": 288,
    "image_size": 288,
    "seed": 0,
    "eval_every": 1
  }
}
```

## 管理页面

入口：左侧菜单“算法训练”，路由 `/manager/trainingJobs`。

- 创建训练：选择算法、数据集和可选 GPU，并根据 JSON Schema 动态生成参数表单
- 任务列表：展示任务编号、算法、数据集、状态、尝试次数、GPU 和提交时间
- 状态操作：排队任务可取消，活动任务可停止，终态任务可重试
- 任务详情：分别查看配置快照、生命周期事件、最终指标和产物索引
- 管理员看到所有任务；普通用户页面只返回自己的任务

## 自动与真实验收记录

- Python 单元测试覆盖参数白名单、路径约束、epoch 上限、固定运行时配置，以及排队任务不会被远程恢复器误判
- 前端生产构建通过
- 未声明参数 `command`：HTTP 400
- 普通用户访问另一用户任务：HTTP 404，自己的列表中不可见
- 排队任务取消：最终 `STOPPED`，事件为 `JOB_CREATED -> JOB_CANCELED`
- 重试：新任务关联原任务，`attempt` 从 1 增至 2
- 真实远程任务：`QUEUED -> STARTING -> RUNNING -> STOPPING -> STOPPED`，退出码 `-15`
- 单用户创建 3 个排队任务后，第 4 个请求被额度限制拒绝；3 个测试任务均已取消
- 真实浏览器检查通过：动态表单、任务列表、详情配置、事件页签均正常，控制台无错误

验收中发现一个旧阶段后端进程仍在运行并扫描相同数据库，导致新排队任务被旧逻辑标记为 `LOST`。已停止该遗留进程，并在新恢复逻辑中增加 `QUEUED` 跳过和 `STARTING` 启动宽限；当前仅保留正在使用的阶段 2 后端。
